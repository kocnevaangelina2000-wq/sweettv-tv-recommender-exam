## Step 3 — methods/components, each alone on validation

All rows use the step-2 protocol: cohort = 4,643 users with ≥ 1 positive in 21-30, test subset = 1,238, pool = 6,363 labelled programmes in the 21-30 schedule, MAP@5 as D16. Each method produces a ranked list for **warm** users (≥ 1 train positive); that list is truncated to 5 and topped up from the user's **shared fallback list** (D17). Cold users get the shared fallback only. `protocol.check_lists` asserts 5 unique pool ids for every user in every row.

## Step 5 — part D: push MAP@5 (select on fold A, report on fold B)

**D50 — decided a priori, before any step-5 fold-B number was computed:** the final re-ranker for `s7_best.csv` is fit on **fold A and fold B rows stacked** (A: features 11-15 → labels 16-20; B: features 11-20 → labels 21-30), then applied to 11-30 features → 31-42. Window lengths differ (A 5+5 weeks, B 10+10, final 20+12), so in that stacked fit the **label is positive count per target week** (A ÷ 5, B ÷ 10), and count/seconds features use the per-week versions where the chosen config has them. Evaluation is unchanged: fit on A, evaluate on B; fold-A scores are 5-fold GroupKFold-by-user out-of-fold. This applies whatever config wins on A; B is not used to choose the final training data.
